# 设计思路

Ako 的名字叫“业务快速启动框架”，但它并不只是一个框架。

更准确地说，Ako 是瞄准“标准数据管理”这一个通用业务场景的**能力集合**。根据你的业务需要，它可以表现为一份协议、一个组件库、一个库、一个框架，或者其中任意几种的组合。

这一页讲清楚三件事：Ako 有哪几种用法，它遵循哪些设计原则，以及它和过去常见的几类方案到底有什么不同。想先看效果，可以去 [Ako 能做什么](/guide/showcase)。

## 同一套能力，多种形态

大多数后台都有一大块重复的工作：菜单、搜索、分页表格、新增编辑表单、枚举翻译、关联选择、行操作。Ako 为这一块准备了从协议到组件的整套能力。用多少、以什么形态用，由你的项目决定：

| 你的需要 | Ako 表现为 | 用到的部分 |
| --- | --- | --- |
| 前后端都自己写，只要一份约定 | 协议 | 菜单、元数据、分页、保存、删除的 [接口约定](/protocol/overview) |
| 在已有的 Vue 页面里放一块标准表格或表单 | 组件库 | 导出的搜索、表格、编辑面板，以及 `createEntityView` |
| 已有后端，只想把模型变成元数据 | 库 | `ako-core` 的注解和元数据转换（不依赖 Rain 或 JPA），或 JavaScript 的 `defineModel` |
| 从零搭一个管理后台 | 框架 | `ako-rain` 或 `ako-spring`，加上前端的 `AkoBootView`，开箱即用 |
| 介于其间 | 任意组合 | 后端用框架、前端只用组件库；或者前端整套使用、后端只按协议实现 |

`ako-spring` 就是一个现成的例子：它没有用 Rain，只把 `ako-core` 当作库，自己接上了 Spring 的容器、事务和 Spring Data。

## 设计原则

### 声明就是唯一的事实

模型的样子只在一个地方定义：后端的模型声明。后端在运行时把声明转换成元数据，前端在运行时读取元数据并渲染页面。

整个过程中没有“生成”这一步，不会产出任何需要维护的中间代码。声明改了，页面就跟着变，不存在“生成的代码和模型不一致”的问题。

### 三方各自演进

前端、后端和框架实现之间只靠一份约定的数据格式对话。只要三方都遵守它，谁升级都不影响另外两方：

- 前端改进了某种字段类型的交互，所有用到这种类型的页面同时受益，后端不用改。
- 后端给模型加了一个字段，搜索、表格、表单同时出现，前端不用发版。
- 后端从 `ako-rain` 换到 `ako-spring`，甚至换成 JavaScript 实现，前端完全感知不到。

### 默认值，而不是限制

Ako 渲染出来的一切都只是“没有特殊需求时的缺省值”。从一个输入框、一块搜索区、一整个页面，到数据来源和 Ako 自己的外壳，每一层都可以单独接管，其余部分照常由声明驱动。后端暂时改不了元数据时，前端还能用 mixin 在本地修改。

这意味着特殊业务不会把你逼到“要么全用 Ako、要么全部放弃”的境地。哪一层有特殊需求，就只在那一层脱离。完整的接管点见 [每一层都能接管](/guide/showcase#每一层都能接管)。

### 按需取用，渐进接入

Ako 不要求你迁移到它上面。已有的 Vue 应用可以把 Ako 嵌进一个菜单或一个页面里；已有的后端可以只为部分模型实现接口。先在一两个标准页面上用起来，再逐步扩大范围，任何时候都可以停下。

### 捆绑深度由你决定

需要坦白的是：依赖 Ako 的能力越多，和 Ako 的捆绑也就越深。只用协议，几乎没有捆绑；同时用上 Ako 的数据页面、鉴权和多租户，替换起来自然就更费力。这是任何一套能力都绕不开的取舍。

Ako 能做的，是让每一份捆绑都是你主动选择的：每项能力都可选、可注入、可组装、可任意替换。哪一层不再适合你，就只换掉那一层的实现，其他能力照常工作。

### 安全留在后端

前端的校验、按钮的二次确认，都只是交互上的便利。权限、唯一性和业务规则由后端负责，每个请求都要重新校验。Ako 不会让你误以为“前端拦住了就安全了”。

## 和其他方案的区别

过去二十年，“快速做出管理后台”这件事大致出现过三类方案。它们各自解决了一部分问题，也各自留下了一部分问题。

### 前端 admin 模板

代表：vue-element-admin、Ant Design Pro，以及各种 xxx-admin。

**它复用的是外壳。** 登录页、布局、侧边栏、标签页、权限菜单、主题，这些模板都帮你做好了。

**它留下的是内容。** 壳里的每一个业务页面，仍然要人一行行写：搜索表单、表格列、分页、编辑弹窗、校验规则、枚举翻译、关联选择。后端再为每个模型写一套接口，前后端靠接口文档对齐字段。

结果是，模板项目的工作量和业务页面的数量成正比。加一个字段要同时改实体、DTO、前端类型、搜索区、表格列、表单和校验，漏掉任何一处就是一个 bug。

**和 Ako 的关系：** 两者并不冲突。Ako 不打算替代模板的外壳，而是接管壳里那些重复的标准页面。已有的 Vue 3 模板项目，可以通过 `AkoApp` 把 Ako 嵌进自己的布局里。

### 后端代码生成器

代表：MyBatis-Plus Generator、JHipster、Rails scaffold，以及各类平台自带的代码生成模块。

**它复用的是第一版代码。** 读一遍数据库表或模型定义，输出 Controller、Service、Mapper、前端页面和 SQL。第一版不用人敲，确实快。

**它的问题在“生成”本身。** 生成出来的代码从那一刻起就归你维护，和模型再无关系：

- 模型改了，要重新生成；
- 重新生成会覆盖文件，写进生成代码里的业务逻辑会被冲掉；
- 为了不被冲掉，团队往往在第一次生成之后就不再生成，回到手工维护。

所以代码生成器节省的是“第一天”的时间，而不是“之后每一天”的时间。生成的代码本质上仍是一份手写代码，只是第一版不是人写的。

**和 Ako 的关系：** 原理正好相反。Ako 没有产物，声明在运行时被解释，模型改了不需要重新生成，自定义业务写在保存钩子、业务接口和自定义组件里，与声明并列，永远不会被覆盖。

### 若依等一体化快速开发平台

代表：若依（RuoYi）、JeecgBoot，以及其他同类的脚手架生态。

**它复用的是一整套系统。** 这类平台通常是一个前后端一体的项目模板：选定了后端框架、ORM、前端框架和 UI 库，内置用户、角色、菜单、部门、字典、日志等系统模块，再配上代码生成器。部分平台还提供在线表单配置，表单定义存在平台的数据库里，由平台在运行时解释。

**它的代价是绑定。** 你得到一套现成的系统，同时也接受了它的全部技术选型和项目结构：

- 业务代码长在平台的项目里，升级平台版本往往意味着手工合并；
- 代码生成部分仍有上一节说的“重新生成会覆盖”的问题；
- 在线表单这类运行时方案，模型定义脱离了业务代码，和平台的数据库、管理界面绑在一起；
- 想换一个后端框架或前端技术栈，基本等于换掉整个平台。

**和 Ako 的关系：** 平台是“你搬进来”，Ako 是“它走进去”。Ako 不规定你的项目结构，而是以协议、组件库、库或框架的形式进入你现有的系统。模型定义始终写在你自己的业务代码里，跟着代码一起评审、一起版本管理。

作为一个完整的业务快速启动框架，Ako 后续也会提供用户、角色、部门、菜单等鉴权模块，以及多租户能力，最终覆盖认证（Authentication）、授权（Authorization）和审计（Accounting）完整的 AAA 能力。但和平台的系统模块不同，这些模块同样是独立的能力：可选、可注入、可组装、可任意替换，前后端都按协议实现。你可以只用 Ako 的数据页面、保留自己的鉴权系统，也可以反过来，只用 Ako 的鉴权。

### 一张表看清差异

| | 前端 admin 模板 | 后端代码生成器 | 若依等一体化平台 | Ako |
| --- | --- | --- | --- | --- |
| 复用的是什么 | 外壳 | 第一版代码 | 整套系统 | 一组可拆分的能力 |
| 业务页面怎么来 | 逐页手写 | 一次性生成，之后手工维护 | 生成，或在平台里在线配置 | 运行时按声明渲染 |
| 模型定义在哪里 | 前后端各写一份 | 数据库表或配置，生成后散落在代码里 | 平台的生成配置或数据库 | 业务代码中的声明，唯一一份 |
| 加一个字段 | 前后端改六七处 | 重新生成，或手工同步 | 重新生成，或在平台里改配置 | 改一处声明 |
| 自定义业务放哪里 | 写在页面里 | 写在生成的代码里，怕被覆盖 | 写在平台项目里，升级要合并 | 钩子、接口、自定义组件，与声明分离 |
| 技术栈 | 前端绑定模板，后端不限 | 绑定生成器支持的栈 | 绑定平台选型 | 协议不限语言，现有 JVM 和 JavaScript 实现 |
| 接入方式 | 从模板起新项目 | 在项目里运行生成器 | 从平台起新项目 | 可以渐进接入已有项目 |
| 特殊页面 | 本来就是手写 | 改生成后的代码 | 改平台代码 | 在需要的那一层单独接管 |

## 什么时候选谁

没有哪种方案适合所有场景。可以按下面的思路判断：

- **页面很少，而且每一页都高度定制**：前端模板加手写就够了，引入任何方案的收益都不大。
- **现在就需要一套现成的用户、角色、权限系统，团队也接受平台的技术选型**：若依这类平台能让你最快拿到一个完整系统。Ako 的鉴权和多租户模块还在规划中。
- **标准的数据管理页面很多，并且要长期迭代**：这正是 Ako 的目标场景。页面越多、模型改得越频繁，“声明即页面”和“三方各自演进”的优势越明显。
- **已经有一个系统在跑**：不必推倒重来。Ako 可以先接管其中一部分标准页面，用得顺手再扩大范围。
